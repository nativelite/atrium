The control plane (ctl)

A fleet is a saved org chart; ctl builds one live, and lets an agent (or you) drive it. With --allow-ctl, a pane can spawn, send to, observe, and kill other agent panes, turning atrium from a viewer of agents into a runtime for them.

What ctl is

The point of doing this inside atrium is legibility. Every agent ctl creates is a visible, killable pane with a status border, listed in the org chart. Because the whole hierarchy is on screen and controllable, atrium coordination stays legible in a way opaque subagents are not.

The shape it is built for is one human, a couple of coordinators, and a wide bench of workers:

  you (a shell/agent pane)
   └─ hand an initiative to →
      lead_a, lead_b          (coordinators)
        └─ each splits it across →
           dev_1, dev_2, …    (workers, each its own pane)

Trust posture (how hands-off spawned agents run, and the ceiling they are capped at) is set with --trust and is covered separately; see trust and security.

Turning it on

The control plane is opt-in and off by default. Without --allow-ctl the channel is not bound and atrium ctl refuses; a session that did not ask for it is unchanged.

atrium --allow-ctl claude                 # bind the control channel
atrium --allow-ctl --trust claude         # …and launch every agent trusted + hands-off
atrium --allow-ctl --max-depth 3 claude   # cap spawn recursion (default 6; 0 = unlimited)

--max-depth <N> bounds spawn recursion so a self-spawning agent cannot fork-bomb the machine. The default is 6; 0 removes the cap. Width is never capped, only recursion depth.

When ctl is on, atrium opens a per-instance control channel (a named pipe on Windows, a unix socket elsewhere; zero-dep, non-blocking-drained in the run loop) and injects two env vars into every pane it spawns:

  • ATRIUM_CTL: the channel endpoint. atrium ctl connects here.
  • ATRIUM_PANE: the caller pane's agent id, so the server attributes each request to its place in the spawn tree.

Any process in a pane (a shell command, or an agent via a tool or hook) issues control by running atrium ctl <cmd>, which speaks one JSON request per line and prints the one-line JSON reply.

A stable endpoint: --ctl-socket

By default the endpoint is named after atrium's process id (\\.\pipe\atrium-ctl-<pid> on Windows, <tmp>/atrium-ctl-<pid>.sock elsewhere), so two sessions never collide and a helper outside the session has to be told the address. To choose it instead:

atrium --allow-ctl --ctl-socket /run/user/1000/atrium.sock claude   # unix: an absolute socket path
atrium --allow-ctl --ctl-socket atrium-main claude                  # Windows: a pipe name (\\.\pipe\atrium-main)
ATRIUM_CTL_SOCKET=/run/user/1000/atrium.sock atrium --allow-ctl up team
  • The flag wins over ATRIUM_CTL_SOCKET, and either one only names the endpoint: the control plane is still switched on by --allow-ctl (or the fleet file). The flag is a session flag and goes before the command, among the others in any order; atrium fleet up <name> and atrium recover, which parse their own flags, take the choice from ATRIUM_CTL_SOCKET.
  • Panes receive the chosen address as ATRIUM_CTL, exactly as they receive the default one.
  • A path with a live listener is refused. If another session is serving on it, the launch ends with atrium: ctl socket <path> could not be bound: a server is already listening on <path> before the terminal is taken, and that session keeps its endpoint. (A resumed or recovered session reports the same failure in the bar and runs without ctl.)
  • A stale path is taken over. On unix a socket file left by a session that was killed refuses a connect; atrium removes it and binds. A file at the path that is not a socket is never removed: the launch fails. A Windows pipe name cannot go stale.
  • What a path may be. On unix an absolute path, short enough for a socket address (under 108 bytes on Linux, 104 on macOS). On Windows a named-pipe name, bare or with the \\.\pipe\ prefix. A comma is refused on both, because Claude Code's teams are handed the address inside TMUX=<address>,<pid>,0.
  • The hardening is unchanged: the socket is 0600 and every peer's uid is checked; the pipe admits the current user only. Choosing the path chooses where the endpoint is, not who may use it.

The discovery file. Every ctl session, with a chosen address or the default, writes ctl/<pid>.endpoint under the per-user state directory (%LOCALAPPDATA%\atrium\sessions on Windows, $XDG_STATE_HOME/atrium/sessions or ~/.local/state/atrium/sessions elsewhere, or ATRIUM_STATE_DIR): one line, the session's address, owner-only. It is removed when atrium exits; a file whose endpoint no longer answers (the session was killed) is treated as stale and removed by the next reader. atrium ctl run outside a pane, with no ATRIUM_CTL, uses it when exactly one session is running, and says so when there are none or several. Outside a pane there is no ATRIUM_TOKEN, so that reaches the token-free reads only.

The board: shared source of truth

send is the ephemeral message stream ("I just shipped auth"); the board is the durable current truth (auth: DONE, owner: Max, url: …). It answers "what is currently true?".

It is a schemaless key → fields tracker living in the atrium daemon. Because atrium is the single broker process every pane talks to, it is a plain map behind the pipe: single writer, no locking, no consensus. A coordinating lead sets tasks and reads board list for status/owner/blocker instead of re-scraping each teammate's transcript; teammates update their own entry as they work.

The board is part of the ctl surface, so it is gated by --allow-ctl. Set ATRIUM_BOARD=<file> to persist it across restarts (in-memory otherwise). Every write records who made it (in the audit log and the entry's by), but the board is shared by the whole session; there are no per-teammate walls.

On top of the plain map, board claim / release give the team a lease: a coordinator (or a worker grabbing a unit of work) claims a key, and a claim succeeds only when the key is free or its previous lease has expired — so two panes cannot both believe they own the same task. The lease has a default TTL (overridable with --ttl), so a claimant that dies never holds the key forever.

The bus: the team's event stream

If the board answers "what is currently true?", the bus answers "what just happened, and does anyone need to act?". A teammate publishes a structured event to a topic (bus pub deploy msg=shipping url=…); teammates pull the topics they subscribe to (bus sub deploy then bus feed). State-only coordination means polling the board; the bus lets a finished worker notify without everyone re-checking.

Two urgency classes carry the visibility-vs-approval split:

  • fyi: the default; cheap, lands on the feed.
  • decision_needed: set with --decision; an escalation that needs a human or lead answer.

Open decisions surface actively: the Ctrl+A b panel lists them first and the status bar shows N decisions need you, so you do not have to be looking. bus resolve <seq> clears one once answered.

Backpressure is designed in, not bolted on, because unread messages cost attention:

  • No echo of your own events.
  • Pull for the record, a bounded wake for the idle: bus feed is the durable record, and you only pay for topics you subscribed to. But a record nobody reads is a silent drop, so an event is also typed into the panes it addresses (--to) and the topic's subscribers, once each is idle — as one framed line, [atrium bus #68 fyi from teammate "builder" on "work" — not operator input] item=F20 status=done commit=3cbec20 (the msg or q, else the fields as k=v). The publisher is never woken; an addressed subscriber is woken once; control characters are stripped so a message can never end its own line. Pending wakes for one pane coalesce into a single delivery, and a pane holds at most 8 undelivered wakes, counted apart from ctl send, so a chatty topic cannot crowd out the operator. Who may wake whom: the publisher's own subtree (as send), the panes above it (a hand-off up to whoever spawned it), and any pane that subscribed — never an unrelated pane by name. This is the one deliberate exception to subtree scoping: the text is a framed, attributed headline of an event the target could read with bus feed anyway, not free text that could pass for the human.
  • Per-agent rate cap of 20 events / 10 s, so one looping worker cannot storm the team.
  • Bounded ring of the oldest 512 events, then they fall off.

Like the board, the bus lives in the single broker process (a plain in-memory log, no locking), is gated by --allow-ctl, records who sent each event, and persists across restarts with ATRIUM_BUS=<file>.

A worked run: initiative to leads to ICs

# You launch the control plane, trusted so the fleet runs hands-off. With
# --trust, every ctl-spawned agent also comes up trusted (no per-action prompts),
# so a lead can drive its ICs without you clicking through dialogs.
atrium --allow-ctl --trust claude

# From your pane, hand the initiative to two coordinators:
atrium ctl spawn --role lead_a -- claude
atrium ctl spawn --role lead_b -- claude
atrium ctl send lead_a "Own the parser rewrite. Split it across two ICs, TDD."
atrium ctl send lead_b "Own the docs refresh. One IC is enough."

# lead_a, from its own pane, builds its team beside it (--here) and tasks them:
atrium ctl spawn --here --role dev_1 -- claude
atrium ctl spawn --here --role dev_2 -- claude
atrium ctl send dev_1 "Rewrite the tokenizer, tests first."
atrium ctl send dev_2 "Rewrite the AST builder, tests first."

# lead_a coordinates by status, not by scraping terminals:
atrium ctl status            # roll-up of lead_a's own subtree
atrium ctl status dev_1      # one IC (lead_b's team is out of scope, refused)

# When an IC is done, its lead reaps it (and anything under it):
atrium ctl kill dev_1

# You see all of it, any time: the org chart and the full trail:
atrium ctl list
atrium ctl audit

The multiplier: many workers, coordinated by a few of them, driven by one human, and every level is a pane you can watch, redirect, zoom into (Ctrl+A z), or kill. ctl is the small verb layer; the panes, tiling, identity injection, and agsess status it stands on already existed.

Reading the control plane from a host

A terminal or dashboard that hosts atrium can read the session's state over the control channel instead of the ATRIUM_BUS sidecar, which it still writes. The channel is \\.\pipe\atrium-ctl-<pid> on Windows and the 0600 socket <tmp>/atrium-ctl-<pid>.sock elsewhere, or the address the operator chose with --ctl-socket (see A stable endpoint); a host that was handed neither reads it from the session's discovery file; one JSON line in, one JSON line out, one request per connection. The verbs that need no token are the reads: list, status, audit, board get, board list, bus feed, bus topics, and from 0.47.0 ping and metrics. Everything that mutates the fleet or its shared state, and every verb that returns a model's words (answer, asked, inbox, who), needs the caller pane's ATRIUM_TOKEN and is scoped to that pane's subtree.

What a host may rely on, from 0.43.0 on:

  • A token-free bus feed is the whole bus. With no caller there are no subscriptions to filter by, so the reply carries every event with seq past since, oldest first, each with its kind and resolved flag; a host derives the open decisions as the decision_needed events whose resolved is false, exactly what the sidecar shows. A pane's own bus feed stays its subscriptions, minus its own echoes.
  • Additive only. A reply object keeps every key it has, with its type; new keys may appear in any release. Read what you know, ignore what you do not.
  • ok is always there. {"ok":true,…} carries the reply; {"ok":false,"err":"<text>"} is the only failure shape. An unauthenticated write fails this way too.
  • Ids are stable within a session. A pane's id is its agent id for the life of the session (the same number as ATRIUM_PANE inside it and %<id> in the tmux shim); parent is null for a root pane.
  • list names the atrium that answered: "atrium":"<version>". Key feature expectations on that, never on the presence of a key.
  • Status words are the agsess vocabulary (working, waiting-approval, waiting-prompt, idle, errored, ended) or null for an unbound pane; idle_ms is milliseconds since the pane's last activity.
  • The sidecar stays. ATRIUM_BUS and ATRIUM_BOARD keep their snapshot format; a host that cannot reach the channel (ctl off, or a sandbox between) falls back to them.
  • ping is the liveness probe (0.47.0). The reply is {"ok":true,"atrium":"<version>","uptime_ms":N}, and it is the run loop that writes it, so an answer means the loop is turning. atrium ctl ping [--timeout <ms>] exits 0 on that answer and prints it; otherwise it exits 1 with one line on stderr that starts no endpoint (ATRIUM_CTL unset, or nothing bound there), connection refused (a unix socket left by an atrium that is gone) or timeout (the endpoint took the connection and the loop did not answer). It asks once (on Windows every other verb retries a missing pipe name for up to 30 s), and the timeout bounds the whole exchange, connect included: 1000 ms by default, 30000 at most. A request that fails any other way, or an answer that is not a ping reply (an atrium older than 0.47.0 refuses the verb), is also exit 1.
  • metrics is counts, and only counts (0.47.0). The reply is {"ok":true,"atrium":"<version>","uptime_ms":N,"panes":{"working":N,"waiting-approval":N,"waiting-prompt":N,"idle":N,"errored":N,"ended":N,"unbound":N},"wakes_delivered":N,"held_inboxes":N,"bus_depth":N,"bus_last_seq":N,"open_decisions":N}: every state key is always there (unbound is a pane with no status, the null of list), wakes_delivered counts bus wake lines handed to a pane since the session started (typed into it, or taken by its mod; events that land together for one pane are one line), held_inboxes the inbox --wait connections open now, bus_depth the events in the ring (512 at most), bus_last_seq the newest event's seq (0 before the first) and open_decisions the unresolved decision_needed events. atrium ctl metrics prints them in the Prometheus text exposition format, and --json prints the reply itself:

``text # HELP atrium_build_info The atrium that answered, as the version label; the value is always 1. # TYPE atrium_build_info gauge atrium_build_info{version="0.47.0"} 1 # HELP atrium_uptime_seconds Seconds since the session's run loop started. # TYPE atrium_uptime_seconds gauge atrium_uptime_seconds 90.500 # HELP atrium_panes Panes by state; unbound is a pane with no agent status. # TYPE atrium_panes gauge atrium_panes{state="working"} 2 atrium_panes{state="unbound"} 1 ``

and in the same way atrium_wakes_delivered_total (a counter), atrium_held_inboxes, atrium_bus_depth, atrium_bus_last_seq and atrium_open_decisions (gauges), with one atrium_panes line per state. The only labels are version and state, and state takes the seven fixed names: no role, title or other text a pane chose is ever a label or a value.

  • Probes are not audited. ping and metrics are answered without an entry in the audit log: asked every few seconds for the life of a session, they would push every real action out of its ring. Every other read is still recorded.

The exact reply shapes are pinned by tests in src/ctl/tests.rs (golden_*); a change that breaks one is a wire change and goes in the changelog as such.

Operator tokens: a caller that is not a pane

Every verb that changes state authenticates as the pane whose ATRIUM_TOKEN matches, and is scoped to what that pane spawned. A control endpoint, a bridge, or a person at another shell is not a pane: it has no token of its own, and borrowing a pane's mislabels the audit log and stops at that pane's subtree. An operator token is the credential for such a caller. It is a named token read from a file; it may use the verbs its entry names, on any pane of the session; and every request made with it, allowed or refused, is audited as operator:<name>.

Without a token file nothing changes: no request can authenticate as an operator, and a write with no pane token is refused as before.

The token file

Give the hosting atrium the file's path, as its first argument or in the environment:

atrium --operator-token-file /run/secrets/atrium-operators --allow-ctl claude
ATRIUM_OPERATOR_TOKEN_FILE=/run/secrets/atrium-operators atrium fleet up crew --allow-ctl

fleet up and recover take the flag anywhere among their own flags. On a plain launch it goes first, because past atrium's own flags the arguments belong to the hosted command. A flag in any other place is an error, never a flag quietly dropped: after another session flag or after the command (atrium --allow-ctl claude --operator-token-file F), atrium stops and says where it goes; before the word ctl, it says the client's flag goes after it. A token file needs the control plane: with --allow-ctl off (and not switched on by the fleet or the recovered session), atrium refuses to start rather than run a session no operator can reach. The flag wins over the variable. The variable holds the path; a token is never read from the environment or from an argument.

The file is JSON:

{"operators": [
  {"name": "bridge",  "token": "5f0c…64 hex characters…", "verbs": ["send", "bus pub", "bus resolve"]},
  {"name": "oncall",  "token": "…", "verbs": ["kill", "respawn", "audit"]}
]}

It is read once, at startup, before any pane exists; changing it means restarting atrium. atrium refuses to start, with the reason on stderr, when:

  • on unix, the file is owned by a user other than the one atrium runs as, or has any permission bit set for its group or for others (chmod 600 it). The check is made on the opened file. On Windows the file's ACL is not checked;
  • it is not a regular file, is over 64 KiB, or is not UTF-8;
  • it is not exactly the shape above: an unknown or repeated key, a missing one, or an empty operators list;
  • a name is not 1 to 24 of A-Z a-z 0-9 _ - (shorter than any token, so a file with the two swapped is refused), or appears twice;
  • a token is shorter than 32 characters or longer than 512, holds anything but A-Z a-z 0-9 . _ ~ + / = - (hex and base64 both fit), repeats fewer than 8 distinct characters, or is shared by two entries. Generate one with openssl rand -hex 32;
  • a verb is unknown, named twice, or one of a pane's own (below).

No error prints a token, and none prints a name from the file either: an entry is named by its position (operator #2). With ctl on, the audit log's first rows record each operator's name and verbs (operator-file).

What an entry may name

VerbsWhat an operator does with them

spawnOpens a worker in a new window, as a top-level caller: depth 1, no parent (see below).
board set, board del, board claim, board releaseWrite the board; the entry's by and a claim's holder are operator:<name>.
bus pub, bus resolvePublish (signed operator:<name>) and resolve decisions. The event wakes the agent panes subscribed to its topic; a pane it only addresses with --to is woken when the entry also names send. No wake is typed into a pane that is not an agent's.
answer, asked, whoModel output: a pane's last answer, the reply to an ask, which panes edited a file. For any pane. Name them only for a caller that should read what the models wrote.
auditThe whole audit log.
list, status, board get, board list, bus feed, bus topics, ping, metricsThe reads the endpoint serves to any caller. An operator gets them whether or not its entry names them, exactly as a caller with no token does. An entry with no verbs at all still has them.

Nothing is granted by default and there is no wildcard: a write the entry does not name is refused. audit is a read with two views: named, it is the whole log; not named, it is the empty list a caller with no credential gets.

Six verbs are about the calling pane and are refused for every operator, and naming one in the file is a startup error: hello, report and whoami (an operator is not a pane and has no mod), inbox (nothing is queued for an operator), bus sub and bus unsub (a subscription wakes the subscribing pane; an operator reads the bus with bus feed).

Where an operator's text may land

send types its text into the target pane and submits it; a bus wake types one framed line. To an agent that is a prompt, and what the agent does with it is bounded by its trust mode. To a shell it is a command line, run with no gate: send 0 "curl … | sh" would be command execution whatever the session's trust. So for an operator:

  • send text may not start with ! or /. An agent CLI gives those a meaning of its own (a shell line, a command of the CLI) instead of reading the text as a prompt.
  • send and ask are refused unless the target is an agent's pane. The test is the command the pane was spawned with (its first word is claude, a claude alias, codex or another agent atrium binds), not what the process is doing at the moment.
  • a bus pub wake is typed into agent panes only, and into a pane the event merely addresses only when the entry also names send: choosing which pane has text typed into it is what send grants. The event is on the bus either way.

This holds for operators. A pane's own send and a pane's bus wake are as they were.

How an operator's spawn is bounded

An operator can never exceed the session's launch trust. Its spawn is run as a top-level caller with no privilege:

  • --mode is capped at the session policy like every caller's, and the reply's note says when it was;
  • the command is a bare name found on PATH (claude, codex): anything with a /, a \ or a : in it is refused. The allowlist looks at a command's file stem and a path is run as given, so \\host\share\claude.exe would pass as claude and run a binary that honours no posture flag;
  • the agent allowlist (ATRIUM_CTL_ALLOW aside, agents only), the argv vetting (no raw permission flags, no --mcp-config, --settings or plugin flags), the depth cap and the pane cap all apply;
  • it may run the worker under the session's own identity or none. A root pane may delegate any identity in the vault; an operator may not;
  • --here is refused: there is no pane to tile beside;
  • the worker has no parent and depth 1. It is an ordinary worker, scoped to what it spawns, and is not a root pane.

respawn keeps the target pane's own mode, capped the same way.

What is checked on every operator request

  1. The token is compared in constant time against the operators only. A pane's ATRIUM_TOKEN sent as an operator token matches nothing, and an operator token sent as a pane token matches no pane: the two travel in different fields (operator_token, token) and are never accepted in each other's place. A request with both is refused.
  2. A token that matches nobody is refused, for a read too, and audited as operator:?. The reply is the same whether the session has a token file or not.
  3. Every field is vetted before it is used: bounded in length, free of control characters and of the Unicode characters that reorder or hide text. A role and a worktree name are plain words (A-Z a-z 0-9 . _ -), because they reach a system prompt, a git ref and a path. send and ask text may span lines and nothing else: an escape, a Ctrl+C or a paste terminator is refused. A request refused here is audited with its fields withheld.
  4. The verb is checked against the entry.

Each step that refuses is audited under the operator's name with the reason. A request that does not parse is recorded too, under the operator whose token it carries (operator:? when the token matches nobody); for every caller, the log keeps the parse error's own words and none of the request's values. An operator's requests are all recorded, empty polls included, with one exception: ping and metrics are answered and not recorded, for an operator as for everyone, because a probe every few seconds would empty the log of everything else (a wrong token on one is still recorded). Otherwise so an operator that polls answer or status fills the 1024-entry ring quickly; mirror the log to a file with ATRIUM_CTL_AUDIT where the history matters. An audit entry for an operator has "caller": null and "by": "operator:<name>"; entries for panes are unchanged and carry no by. A worker's own ctl audit never shows an operator's entries.

ctl spawn refuses, for every caller, a role that would read as an operator's label: operator itself (the label of a write with no pane behind it), anything starting operator:, and their look-alikes. Whitespace and characters that do not show are ignored for the comparison; a letter that is not ASCII counts as a possible stand-in for the Latin one; operator followed by any mark other than _ or - is refused; and a role with a : in it must otherwise be plain ASCII (A-Z a-z 0-9 . _ -). operators, operator_2 and team:alpha are ordinary roles. So nothing on the board or the bus signed operator:<name> came from a pane ctl spawn created. A fleet file's role names are a person's and are not checked.

From the client

export ATRIUM_CTL=<the session's endpoint>
atrium ctl --operator-token-file ~/.config/atrium/bridge.token kill dev_3
atrium ctl --operator-token-file operators.json --operator oncall audit 50

The flags go after ctl and before the verb; atrium --operator-token-file F ctl … is an error that says so. The file is either the hosting atrium's own (pick the entry with --operator <name>; it may be omitted when the file names one) or a single token on one line, which is what to hand a client that should know one token and not the others. The same ownership and permission rule applies. The client sends the token as operator_token and sends no pane id and no pane token, even when it runs inside a pane. wait and ask work the same way.

On the wire it is one more field of the one-line request: {"operator_token":"…","cmd":"kill","target":"dev_3"}.

What protects the token, and what does not

  • It never enters a pane's environment. atrium removes ATRIUM_OPERATOR_TOKEN_FILE from its own environment before the first pane is spawned, and the token itself is never in an environment or on a command line.
  • It is in no log, reply, bar message or debug output. The audit log records names; an unparseable request is logged by its length and the parse error's own words; the types that hold a token (the loaded file, a parsed request) print <redacted>.
  • File permissions do not stop a pane. Panes run as the same user as atrium. A 0600 file keeps other users out; it does not keep out an agent in a pane, which can read any file its user can, and on Linux can read the path from /proc/<atrium pid>/cmdline or /proc/<atrium pid>/environ even though its own environment does not have it. Removing the variable is hygiene, not a boundary.
  • What does stop a pane is the deployment: mount the file where the panes' processes cannot read it (a path outside what the agent's sandbox exposes), run the panes under a sandbox or a different user, or keep the token file on the client's side of a boundary and give the host a file only it can read. If a pane can read the file, treat every pane as holding every operator's verbs.
  • The token is the whole credential. Anything that can reach the control channel and present it is that operator, a pane included. The channel itself admits only the same user (a 0600 socket with a peer-credential check; a pipe whose ACL names the logon session), so an operator at another machine reaches it through something you put in front of it. Give each caller its own entry with the fewest verbs, so the audit log names who did what and a leaked token is one line to remove.
  • An operator with send can make any agent do what that agent's trust mode allows, and no more. send types a prompt into an agent's pane as the human would, and the agent acts on it under the mode it was started with. In a skip session that is anything; in a plan session it is reading. The launch trust is the ceiling, which is why an operator can never raise it, and why the text is refused for a pane that is not an agent's: a shell has no mode. What this does not cover: whatever else an agent CLI's input line treats specially beyond a leading ! or / (atrium types the text; the CLI decides what it is), and a pane whose command is an agent's name but resolves to something else on PATH. The first is the agent's input handling; the second is whoever controls PATH and the working directory of the hosting atrium.
  • kill and respawn reach the human's own panes. An operator that holds them can end the session.

The mod: typed tools, the role section and subagent panes

With atrium mod install done, every claude pane carries a plugin (the mod, mod/) that speaks the verbs above for it and gives the model three things:

  • Typed tools. atrium_spawn, atrium_send, atrium_status, atrium_list, atrium_kill, atrium_board_set|get|list|claim|release and atrium_bus_pub|feed|resolve|topics: each call is one atrium ctl run with the pane's own token, and the reply is what the model reads. The shell verbs stay the same surface, so the skills and the docs remain true either way. A permission ask for one of these tools is answered by the mod, never a dialog; a deny from a rule stands.
  • The role section. An atrium:role section of the system prompt, from whoami: the pane, its role, parent, depth and trust mode, its item on the board and the files that item owns, its worktree, whether it may spawn, and what a [atrium bus # line is. Re-read every turn, so a lead's re-brief lands. When the item owns files, an Edit, Write or NotebookEdit anywhere else is refused by real path with the owner named.
  • Native delivery. A pane whose mod declared inbox is never typed into: its sends and wakes wait in the queue until the mod collects them with inbox and submits each through the engine's prompt queue, which starts a turn only when the session is idle. The draft and dialog races the pty path guards against (src/deliver.rs) do not arise, and a task may span lines. A pane without the cap keeps the pty path.
  • The /atrium pane. Inside Claude Code, /atrium opens a pane with the open decisions (each with a resolve button and a hotkey), the board, and the last bus events the pane subscribes to, refreshed every 3 s while open; a band above the prompt counts the open decisions and opens the pane. With a fleet's respawn_at, a pane whose context fill crosses the threshold while idle gets one decision_needed posted to its parent on the atrium topic, with the parent woken: the lead's "respawn when heavy" rule becomes a number it is asked about.
  • Sight: captions, the collision radar and asks. The mod reports a caption on every tool call, free of charge (running cargo test, editing filter.rs, reading main.rs) and, when the fleet says captions: true, a six-word caption from the model's own words every twenty seconds or so of streaming (one small haiku call); the overview shows it in place of the transcript's last action and the tile draws it dim after the title. It reports the real path of every Edit, Write and NotebookEdit that ran, and the broker keys each by the pane's worktree, so two worktrees' copies of src/x.rs are one file: the first time two live panes edit it, both tiles and overview rows wear ⚡, the overview lists the file under the agents, and one collision decision_needed goes to the nearest pane above both (the lead) on the atrium topic, or to the human when there is none. atrium ctl who <path> answers who has a file, before the merge. And atrium ctl ask <target> <question> (or Ctrl+A ? on a tile, or atrium_ask from a pane) puts a question to a pane's mod, which answers from a fork of the pane's own context: the turn is untouched, nothing is appended to its context, and the transcript never leaves the pane; the reply opens as an overlay for the human and returns as the tool's result for an agent.
  • Subagents as panes. Under the session's subagents policy (panes, the default; a fleet may say native or deny), the model's Agent tool is refused with a pointer to atrium_subagent, which spawns a claude pane beside the caller (--here), sends it the task, waits for the answer the child's own mod reports, closes the pane unless keep or the fleet's subagents_keep, and returns the answer. Every subagent is a tile the human can watch, send to and kill.

What the broker believes of a mod is bounded: a report is about the reporter (a target is refused), an answer is capped, scrubbed and read only up the spawn tree, and a mod cannot widen trust (it rewrites an ask to allow for its own tools only; a deny is never overridden). See trust and security.

Delegation skills: atrium-delegate, atrium-coordinate and atrium-fleet

ctl is the mechanism; three Claude Code skills (in skills/) are the instruction layer that makes an agent use it. Copy the directories into ~/.claude/skills/ and any atrium-hosted claude picks them up. The first two exist because the trigger is who decides to delegate:

  • atrium-delegate (ambient / discretionary): the agent may hand off an independent, substantial part when it genuinely pays, and does small or dependent work inline. On its own a capable agent usually judges it can do the work itself (which is correct), so this fires rarely by design. Its real value is discoverability: without it, an agent does not know atrium ctl exists at all.
  • atrium-coordinate (directed): for when you want fan-out. It casts the agent as a coordinator that splits the work, delegates every part, monitors, collects, and reaps, instead of implementing inline. This is the reliable lever: on a task where the ambient skill chose inline every time, coordinate mode fanned out every time.

The third covers the saved-fleet path rather than ad-hoc delegation:

  • atrium-fleet: designing, configuring and running an atrium.fleet.json — the file's full schema, what the resource budget actually costs (compiling is the scarce resource), what atrium enforces, and how to read the PREFLIGHT block.

Drop a spawned lead straight into coordinate mode by telling it to coordinate:

atrium ctl spawn --role lead -- claude
atrium ctl send lead "Coordinate this across a team, one teammate per part: <the initiative>"

or, from your own pane, just say "coordinate this across a team: …" and let the skill surface.

With codex. codex reads the same SKILL.md format. Copy the three directories into ~/.agents/skills/ (all your projects) or a repo's .agents/skills/ (that repo), or add the plugin marketplace with codex plugin marketplace add nativelite/marketplace. A codex pane does not need the skills to know ctl exists: with the control plane on, atrium gives it the same directive it gives claude, as -c developer_instructions. Its commands reach the control socket through its sandbox as described in codex panes.

Claude Code's own teams, as atrium panes

Claude Code has a teams feature of its own: a lead spawns teammates, hands them tasks from a shared list, and messages them through mailboxes. In split-pane mode each teammate gets a pane, but Claude Code does not draw panes. It runs a program named tmux (split-window -d -t @0 -h -l 70% -P -F '#{pane_id}' -- claude --agent-name …), reads the new pane's id back, and later kill-panes it. Its backend knows two pane managers, tmux and iTerm2, and picks tmux whenever TMUX is set in the lead's environment. On Windows there is neither, so teams fell back to in-process rows inside the lead.

With the control plane on, atrium answers to the name. A claude pane in an --allow-ctl session is born with:

  • TMUX=<ctl address>,<atrium pid>,0 and TMUX_PANE=%<pane>: what Claude Code's auto-detection looks for;
  • a PATH led by <state root>/shim/, holding tmux (tmux.exe on Windows, since the native Claude Code resolves executables only). It is atrium's own binary under a second name, placed on the first claude spawn and refreshed when atrium is reinstalled;
  • CLAUDE_CODE_TMUX_TRUECOLOR=1, so Claude Code keeps truecolor instead of assuming a real tmux in between.

Invoked as tmux, atrium serves the verbs the teams backend uses, each one an atrium ctl request with the caller's own token: -V, display-message -p, list-panes -F, list-windows -F, split-window, new-window, kill-pane and send-keys. Layout and style verbs (set-option, select-pane, select-layout, resize-pane, show-environment, has-session, new-session, switch-client, attach-session) are honoured by doing nothing. capture-pane is refused: atrium never hands one pane the text of another. Anything else exits 1 with a message.

So a teammate is an ordinary atrium pane: split-window is ctl spawn --here (--no-focus for tmux's -d, which Claude Code passes, so your keyboard stays where it is), the pane's role is the teammate's --agent-name, it is a child of the lead in the spawn tree and under its trust ceiling, and it has the status border, the overview row, the board and the bus. The shim models one window, @0, whose panes are the caller and its direct children, which is the team as the lead sees it; pane ids are %<agent id>.

Where a teammate lands follows the split's target. Claude Code's first teammate splits the window (-t @0), so it goes beside the lead; each later one splits an existing teammate's pane (-t %N -v or -h), and the shim passes --beside <N> so the new pane goes next to that teammate. A target that is not in the lead's window falls back to the lead, and the spawn reply's note says so. The split's size is honoured: the shim passes -l as --size, so the first teammate's -l 70% gives it 70 % of the lead's width and the lead keeps 30 %. The ratio lives on the split, so a terminal resize keeps the share, and a later teammate (-t %1 -v, no -l) re-grids only the half it lands in: the teammates tile inside their 70 % and the lead's 30 % does not move, as under tmux. A -l in cells (-l 20) is that many columns of the target pane. -h and -v are accepted too; the window's own orientation decides.

The team's task list shows in the overview (Ctrl+A o). Claude Code keeps a team under ~/.claude/teams/<team>/ (config.json: the lead and the members; inboxes/: their mailboxes) and its tasks under ~/.claude/tasks/<team>/, one JSON file per task with its subject, status (pending, in_progress, completed), owner and blockedBy. The team is named session- plus the first eight characters of the lead's session id, which atrium minted at spawn, so atrium knows where to look without being told ($CLAUDE_CONFIG_DIR is honoured). Under the lead's row the overview lists the team, one line per task: [ ] pending, [~] in progress, [x] completed, each with its owner and the tasks still blocking it; a teammate's row carries its current task as the caption when its mod reported none. The files are read only while the overview is open, at most once a second, and only a file whose stamp changed is read again. The team leaves the overview when the lead's session ends and Claude Code removes the team directory (the tasks directory stays behind, and is not a live team). The files are Claude Code's: atrium never writes them.

Three things to know:

  • It is a setting. "teams": "off" in config.json turns it off for every session on the machine; teams: "off" in a fleet turns it off for that fleet, and a fleet's own key wins over the config's. "show" is the default. Off means the pane gets no TMUX and nothing on its PATH, so Claude Code's teams run in-process as they did before. The fleet preflight names which is in effect.
  • Claude Code's teammateMode setting defaults to in-process. Set it to auto (split panes when inside tmux, which an atrium claude pane now is) or tmux.
  • atrium --tmux-shim <tmux args…> reaches the shim by its real name, for a probe: atrium --tmux-shim -V prints tmux 3.5a-atrium.

The shim speaks only for the pane that runs it, with that pane's token, so it can spawn and kill only inside that pane's subtree, like any atrium ctl caller.
