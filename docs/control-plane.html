The control plane (ctl)

A fleet is a saved org chart; ctl builds one live, and lets an agent (or you) drive it. With --allow-ctl, a pane can spawn, send to, observe, and kill other agent panes, turning atrium from a viewer of agents into a runtime for them.

What ctl is

The point of doing this inside atrium is legibility. Every agent ctl creates is a visible, killable pane with a status border, listed in the org chart. Because the whole hierarchy is on screen and controllable, atrium coordination stays legible in a way opaque subagents are not.

The shape it is built for is one human, a couple of coordinators, and a wide bench of workers:

  you (a shell/agent pane)
   └─ hand an initiative to →
      lead_a, lead_b          (coordinators)
        └─ each splits it across →
           dev_1, dev_2, …    (workers, each its own pane)

Trust posture (how hands-off spawned agents run, and the ceiling they are capped at) is set with --trust and is covered separately; see trust and security.

Turning it on

The control plane is opt-in and off by default. Without --allow-ctl the channel is not bound and atrium ctl refuses; a session that did not ask for it is unchanged.

atrium --allow-ctl claude                 # bind the control channel
atrium --allow-ctl --trust claude         # …and launch every agent trusted + hands-off
atrium --allow-ctl --max-depth 3 claude   # cap spawn recursion (default 6; 0 = unlimited)

--max-depth <N> bounds spawn recursion so a self-spawning agent cannot fork-bomb the machine. The default is 6; 0 removes the cap. Width is never capped, only recursion depth.

When ctl is on, atrium opens a per-instance control channel (a named pipe on Windows, a unix socket elsewhere; zero-dep, non-blocking-drained in the run loop) and injects two env vars into every pane it spawns:

  • ATRIUM_CTL: the channel endpoint. atrium ctl connects here.
  • ATRIUM_PANE: the caller pane's agent id, so the server attributes each request to its place in the spawn tree.

Any process in a pane (a shell command, or an agent via a tool or hook) issues control by running atrium ctl <cmd>, which speaks one JSON request per line and prints the one-line JSON reply.

A stable endpoint: --ctl-socket

By default the endpoint is named after atrium's process id (\\.\pipe\atrium-ctl-<pid> on Windows, <tmp>/atrium-ctl-<pid>.sock elsewhere), so two sessions never collide and a helper outside the session has to be told the address. To choose it instead:

atrium --allow-ctl --ctl-socket /run/user/1000/atrium.sock claude   # unix: an absolute socket path
atrium --allow-ctl --ctl-socket atrium-main claude                  # Windows: a pipe name (\\.\pipe\atrium-main)
ATRIUM_CTL_SOCKET=/run/user/1000/atrium.sock atrium --allow-ctl up team
  • The flag wins over ATRIUM_CTL_SOCKET, and either one only names the endpoint: the control plane is still switched on by --allow-ctl (or the fleet file). The flag is a session flag and goes before the command, among the others in any order; atrium fleet up <name> and atrium recover, which parse their own flags, take the choice from ATRIUM_CTL_SOCKET.
  • Panes receive the chosen address as ATRIUM_CTL, exactly as they receive the default one.
  • A path with a live listener is refused. If another session is serving on it, the launch ends with atrium: ctl socket <path> could not be bound: a server is already listening on <path> before the terminal is taken, and that session keeps its endpoint. (A resumed or recovered session reports the same failure in the bar and runs without ctl.)
  • A stale path is taken over. On unix a socket file left by a session that was killed refuses a connect; atrium removes it and binds. A file at the path that is not a socket is never removed: the launch fails. A Windows pipe name cannot go stale.
  • What a path may be. On unix an absolute path, short enough for a socket address (under 108 bytes on Linux, 104 on macOS). On Windows a named-pipe name, bare or with the \\.\pipe\ prefix. A comma is refused on both, because Claude Code's teams are handed the address inside TMUX=<address>,<pid>,0.
  • The hardening is unchanged: the socket is 0600 and every peer's uid is checked; the pipe admits the current user only. Choosing the path chooses where the endpoint is, not who may use it.

The discovery file. Every ctl session, with a chosen address or the default, writes ctl/<pid>.endpoint under the per-user state directory (%LOCALAPPDATA%\atrium\sessions on Windows, $XDG_STATE_HOME/atrium/sessions or ~/.local/state/atrium/sessions elsewhere, or ATRIUM_STATE_DIR): one line, the session's address, owner-only. It is removed when atrium exits; a file whose endpoint no longer answers (the session was killed) is treated as stale and removed by the next reader. atrium ctl run outside a pane, with no ATRIUM_CTL, uses it when exactly one session is running, and says so when there are none or several. Outside a pane there is no ATRIUM_TOKEN, so that reaches the token-free reads only.

What a pane's request is held to

A pane's token says which pane is asking, and an agent in a pane is held to the session's launch trust. These rules keep a ctl request from being a way around that. Each refusal names its reason and the way on.

spawn names a bare command, and runs the file it names on PATH. The command after -- is 1 to 64 of A-Z a-z 0-9 _ -, not starting with -: no /, \ or :, so no path of any kind, and no ., so no extension. The allowlist reads a command by its file stem and a path is run as given, so \\host\share\claude.exe or ./x/claude.sh would pass as claude and start a program that ignores the posture flags atrium appends; and claude.bat, claude.exe (where claude is an npm shim) or claude. would pass the same way, be found nowhere on PATH, and be run from the pane's working directory. atrium then looks the name up itself, on every platform, over the absolute directories of PATH: on Windows with the system's PATHEXT, elsewhere the name as it is, which must be a regular file with an execute bit. It spawns that file by its full path (and records it), and refuses a name it does not find. An empty or relative entry (., ./node_modules/.bin) is skipped: it names a folder inside the project, or inside the worktree a spawn asks for, where a pane could plant a file called codex. This holds for every caller. A fleet file's cmd is not a ctl request and may be a path; respawn replays the command atrium recorded for the pane, and no request changes that record; a spawn with no command starts the caller's recorded one, a fleet-approved path included. (One pane gets its command second-hand, and still from atrium: a teammate placeholder, which runs atrium's own waiting program until its lead's Claude Code starts a teammate in it, once, with the lead pane's own recorded program.)

A Claude Code teammate is started by atrium, not by the line that asks for it. Since Claude Code 2.1.325 a lead starts a split-pane teammate by handing tmux one shell command line (cd … && env … claude --agent-id …). Through atrium's tmux shim that line is a ctl request from the lead's pane, and it is never run, by a shell or otherwise. atrium parses it against one grammar, starts the lead pane's own claude instead of the program it names, passes on only the flags in a closed table, turns its permission flags into a request that is capped at the lead pane's mode and at the session's, gives the teammate the environment atrium gave its lead plus three team variables and the variables you listed in teams_env (every other assignment on the line is dropped, and named when it would have differed), and starts it where its lead is: a line that names any other directory is refused. Anything it does not recognise refuses the launch. The whole of it is under Claude Code's own teams.

An argument of a spawned agent's command may not open with !, /, # or @. A positional argument is the new agent's first prompt, and an agent CLI reads a prompt that starts with one of those as a shell line, a command of its own, a memory note or a mention. This is the one rule here that is a list of characters: atrium cannot put its header in front of an argument, so it refuses the openers it knows, on every argument of an agent CLI's command (below skip for a pane, at any trust for an operator). It refuses some harmless arguments too: a prompt that really starts with #, or codex -i /abs/image.png. A command you allowed beside the agents with ATRIUM_CTL_ALLOW keeps its own arguments (cmd /Q). To hand a new agent text that starts with one of these, spawn it and send the text.

send reaches an agent's pane. Text is typed into the target and submitted. To an agent that is a prompt, bounded by its trust mode; to a shell it is a command line, run with no gate. A send whose target was not spawned as an agent CLI (claude, a claude alias, codex, gemini, aider, cursor-agent) is refused unless the session was launched at --trust skip. No --trust at all counts as below skip. The test is the command the pane was spawned with; a command you added with ATRIUM_CTL_ALLOW is not an agent for this, a wrapper around one included. One case is taken at any trust: a pane whose own mod declared inbox collects its deliveries itself and nothing is typed into it; if that mod is gone before it collected (the pane was respawned), the delivery is dropped and its sender is told.

Every send into an agent starts with atrium's header. What is delivered is [atrium: from <label>] and then the text, on one line with the start of the text. The label is the broker's own record of the sender, never a field of the request. Every label there is:

A pane's send to itself is headed too, and so is a send handed to a mod's inbox, so a message reads the same whichever way it arrives. The point is the first character: on an empty prompt, no character a caller chose is the first one. A text that starts with !, /, # or @ is delivered and read as text. There is no list of special openers to keep up with the CLIs, and nothing is refused for how it starts. (The bus frame still names a role-less pane pane N counting from 1, as it always has: pane 1 there is ctl id 0. That mismatch is open.)

Neither frame can be forged. atrium writes two frames into a prompt: this header, and the bus wake's [atrium bus #7 … from teammate "x" …]. In every piece of caller-supplied text that reaches either (a send's text, a wake's body, detail, sender label and topic, the file and role names in a decision atrium posts), an opening square bracket or a look-alike (fullwidth, CJK, mathematical) that is followed, after any whitespace and hidden characters, by atrium in any case becomes (. So a wake cannot carry [atrium: from operator:x] … up the tree, and a send cannot carry a second bus line.

One send is one prompt. A line break inside the text must not submit, or the next line would open a fresh prompt with a character of the caller's choosing. A multi-line brief therefore arrives as lines where a paste or the mod carries it, and as one line with ↵ marks on the flat path, which on Windows is every agent's pane without the mod, at skip too. A bus wake was always one line.

One delivery at a time per pane. A delivery is in flight from its first byte to its Enter. While one is, every other delivery for that pane waits, and for 1.5 s after the Enter before the pane's readiness is asked again. So an Enter submits exactly the delivery it belongs to: two sends that become ready together are text, Enter, text, Enter, and a command never shares a line with a send or a wake.

A send is plain text. Below skip, a pane's text may hold no control character but a newline and a tab, and none of these characters that do not show as themselves: the line and paragraph separators (U+2028, U+2029), the bidi embeddings, overrides, isolates and marks (U+200E, U+200F, U+202A–202E, U+2066–2069, U+061C), the zero-width spaces and joiners (U+200B–200D, U+2060–2064, U+FEFF), the soft hyphen (U+00AD), the Hangul fillers (U+115F, U+1160, U+3164, U+FFA0), the Mongolian vowel separator (U+180E), the variation selectors (U+FE00–FE0F, U+E0100–E01EF) and the tag characters (U+E0000–E007F). In a terminal program a control character is a key: ESC [ Z (Shift+Tab) cycles Claude Code's permission mode, ESC [ 201 ~ ends a paste early, a CSI-u sequence spells any key, Ctrl+C, Esc and the arrows drive a dialog. \r\n is taken as a newline; a carriage return on its own is an Enter and is refused. At skip a pane's text is not vetted; it still goes through the delivery forms above, so into a Windows agent pane its line breaks are flattened.

A delivery waits for a prompt, and a dropped one is reported. A delivery is typed when the target is at its prompt as far as atrium can tell: an agent with a status only when idle or waiting for a prompt, never while a tool call is unresolved or the human has typed a draft in the pane in the last five minutes; a claude or codex pane with no status yet only once its prompt hint is on screen and still, and never while one of codex's startup screens is up. Until 0.47.0 such a pane was typed into anyway after 300 s; now the delivery is dropped, because the text would be keystrokes into whatever is showing. A delivery is also dropped when its target has exited, or is no longer a pane text may be typed into. A drop is never silent: the bar says it, the audit log gets a delivery-dropped row under the sender, and a sending pane that is an agent's is sent one fyi on the atrium topic, in atrium's own words (which pane, why, and that nothing was typed). That notice has no sender, so if it cannot be delivered either, the audit row is all there is.

A slash command goes through command, and the human's list. Since a send can no longer be a command of the agent CLI, atrium ctl command <target> /<name> is the way to run one: the name is typed as its own prompt line with no header, then Enter, when the pane is at its prompt. It is delivered only when /<name> is in the session's commands list, which is empty by default and comes from the human: "commands": ["/compact", "/clear"] in the user config, or in a fleet, whose own list replaces the config's and is shown in the launch banner. A session brought back with atrium recover uses the config's list, not the fleet's. A name is / then 1 to 64 of a-z A-Z 0-9 _ - :, checked when the file is loaded; nothing a ctl request says adds to the list. There are no arguments in this release: anything after the name is refused. The target is an agent's pane in the caller's own subtree, at any trust; a pane that is not an agent's is refused even with a mod's inbox. ! is not expressible. The audit row carries the name. atrium types the name; whether the target's CLI has such a command is the CLI's.

A listed command is a grant. Every pane that can reach another may run it there. /compact and /clear cost a teammate its context; /permissions, /add-dir, /plugin, /mcp or a custom command hand the sender whatever that command can change, in a pane that may be at a different posture than its own. List the ones you mean a lead to use, and nothing else.

A wake is typed into an agent's pane. The same rule as send for the framed line a bus event becomes: a pane that is not an agent's is not woken (unless its mod takes its inbox), whether it subscribed or was addressed, and whether a pane published the event or atrium did (the collision and respawn decisions). For a pane's publish that holds below skip; for an operator's, at any trust. The event is on the bus either way, and the publisher's reply says so: "note": "not woken: pane 0 is not an agent's pane …", with that pane left out of subscribers. The frame does not make a wake safe for a shell: only control characters are removed from its body, so &, |, ;, a backquote and $(…) stay, and cmd.exe handed [atrium bus #7 …] done & calc runs calc. At skip that still holds for a pane's publish: a wake is typed into a shell pane that subscribed or is addressed, and the shell runs what follows an &. Nothing is gated at skip; a shell pane that should not run a teammate's text should not subscribe. A wake always opens with [atrium bus # and is one line (line breaks in a field become spaces).

What does not type: ask is handed to the target's mod over its inbox and answered from a fork with no tools, so it is as it was; a fleet's kickoff is the last argument of the command in the fleet file, not a ctl request. The keyboard is not a ctl caller: what you type into a pane is yours.

What this does not cover.

  • A prompt that is not empty. The header is first only when the prompt is empty. atrium holds a delivery while the human has a draft in the target pane, but a draft untouched for 300 s counts as abandoned: the delivery is then appended to it and submitted with it.
  • A dialog atrium cannot see. An agent whose status reads idle while it shows a picker or a question of its own (not a tool-use approval, which is held) is typed into. So is gemini, aider or cursor-agent two seconds after its screen went still, whatever it shows: atrium has no prompt hint for them.
  • What the CLI does with the middle of a prompt: an @path mention inside a sentence, say.
  • PATH itself. It is trusted as the human set it. An absolute entry is searched wherever it points, one inside the project included: with C:\work\app\node_modules\.bin (or /work/app/node_modules/.bin) on PATH, a pane that can write there can supply the codex a spawn finds.
  • What a pinned command runs. On Windows a claude installed with npm is a .cmd shim that starts node by name, and cmd.exe looks for node in the pane's working directory before PATH. (atrium does not set NoDefaultCurrentDirectoryInExePath, which would change what an agent's own commands find.)
  • A wrapper allowed through ATRIUM_CTL_ALLOW: it is spawned with the arguments given and without the argument rule, and what it runs is its own business.
  • Multi-line text on Windows arrives flattened unless the pane has the mod.

The board: shared source of truth

send is the ephemeral message stream ("I just shipped auth"); the board is the durable current truth (auth: DONE, owner: Max, url: …). It answers "what is currently true?".

It is a schemaless key → fields tracker living in the atrium daemon. Because atrium is the single broker process every pane talks to, it is a plain map behind the pipe: single writer, no locking, no consensus. A coordinating lead sets tasks and reads board list for status/owner/blocker instead of re-scraping each teammate's transcript; teammates update their own entry as they work.

The board is part of the ctl surface, so it is gated by --allow-ctl. Set ATRIUM_BOARD=<file> to persist it across restarts (in-memory otherwise). Every write records who made it (in the audit log and the entry's by), but the board is shared by the whole session; there are no per-teammate walls.

On top of the plain map, board claim / release give the team a lease: a coordinator (or a worker grabbing a unit of work) claims a key, and a claim succeeds only when the key is free or its previous lease has expired — so two panes cannot both believe they own the same task. The lease has a default TTL (overridable with --ttl), so a claimant that dies never holds the key forever.

The bus: the team's event stream

If the board answers "what is currently true?", the bus answers "what just happened, and does anyone need to act?". A teammate publishes a structured event to a topic (bus pub deploy msg=shipping url=…); teammates pull the topics they subscribe to (bus sub deploy then bus feed). State-only coordination means polling the board; the bus lets a finished worker notify without everyone re-checking.

Two urgency classes carry the visibility-vs-approval split:

  • fyi: the default; cheap, lands on the feed.
  • decision_needed: set with --decision; an escalation that needs a human or lead answer.

Open decisions surface actively: the Ctrl+A b panel lists them first and the status bar shows N decisions need you, so you do not have to be looking. bus resolve <seq> clears one once answered.

Backpressure is designed in, not bolted on, because unread messages cost attention:

  • No echo of your own events.
  • Pull for the record, a bounded wake for the idle: bus feed is the durable record, and you only pay for topics you subscribed to. But a record nobody reads is a silent drop, so an event is also typed into the panes it addresses (--to) and the topic's subscribers, once each is idle — as one framed line, [atrium bus #68 fyi from teammate "builder" on "work" — not operator input] item=F20 status=done commit=3cbec20 (the msg or q, else the fields as k=v). The publisher is never woken; an addressed subscriber is woken once; control characters are stripped so a message can never end its own line. Pending wakes for one pane coalesce into a single delivery, and a pane holds at most 8 undelivered wakes, counted apart from ctl send, so a chatty topic cannot crowd out the operator. A wake is typed only into an agent's pane: below --trust skip a shell pane that subscribed or is addressed is not woken, because a shell would run the line (what a pane's request is held to). Who may wake whom: the publisher's own subtree (as send), the panes above it (a hand-off up to whoever spawned it), and any pane that subscribed — never an unrelated pane by name. This is the one deliberate exception to subtree scoping: the text is a framed, attributed headline of an event the target could read with bus feed anyway, not free text that could pass for the human.
  • Per-agent rate cap of 20 events / 10 s, so one looping worker cannot storm the team.
  • Bounded ring of the oldest 512 events, then they fall off.

Like the board, the bus lives in the single broker process (a plain in-memory log, no locking), is gated by --allow-ctl, records who sent each event, and persists across restarts with ATRIUM_BUS=<file>.

A worked run: initiative to leads to ICs

# You launch the control plane, trusted so the fleet runs hands-off. With
# --trust, every ctl-spawned agent also comes up trusted (no per-action prompts),
# so a lead can drive its ICs without you clicking through dialogs.
atrium --allow-ctl --trust claude

# From your pane, hand the initiative to two coordinators:
atrium ctl spawn --role lead_a -- claude
atrium ctl spawn --role lead_b -- claude
atrium ctl send lead_a "Own the parser rewrite. Split it across two ICs, TDD."
atrium ctl send lead_b "Own the docs refresh. One IC is enough."

# lead_a, from its own pane, builds its team beside it (--here) and tasks them:
atrium ctl spawn --here --role dev_1 -- claude
atrium ctl spawn --here --role dev_2 -- claude

atrium ctl send dev_2 "Rewrite the AST builder, tests first."

# You see all of it, any time: the org chart and the full trail:

The multiplier: many workers, coordinated by a few of them, driven by one human, and every level is a pane you can watch, redirect, zoom into (Ctrl+A z), or kill. ctl is the small verb layer; the panes, tiling, identity injection, and agsess status it stands on already existed.

Reading the control plane from a host

A terminal or dashboard that hosts atrium can read the session's state over the control channel instead of the ATRIUM_BUS sidecar, which it still writes. The channel is \\.\pipe\atrium-ctl-<pid> on Windows and the 0600 socket <tmp>/atrium-ctl-<pid>.sock elsewhere, or the address the operator chose with --ctl-socket (see A stable endpoint); a host that was handed neither reads it from the session's discovery file; one JSON line in, one JSON line out, one request per connection. The verbs that need no token are the reads: list, status, audit, board get, board list, bus feed, bus topics, and from 0.47.0 ping and metrics. Everything that mutates the fleet or its shared state, and every verb that returns a model's words (answer, asked, inbox, who), needs the caller pane's ATRIUM_TOKEN and is scoped to that pane's subtree.

What a host may rely on, from 0.43.0 on:

  • A token-free bus feed is the whole bus. With no caller there are no subscriptions to filter by, so the reply carries every event with seq past since, oldest first, each with its kind and resolved flag; a host derives the open decisions as the decision_needed events whose resolved is false, exactly what the sidecar shows. A pane's own bus feed stays its subscriptions, minus its own echoes.
  • Additive only. A reply object keeps every key it has, with its type; new keys may appear in any release. Read what you know, ignore what you do not.
  • ok is always there. {"ok":true,…} carries the reply; {"ok":false,"err":"<text>"} is the only failure shape. An unauthenticated write fails this way too.
  • Ids are stable within a session. A pane's id is its agent id for the life of the session (the same number as ATRIUM_PANE inside it and %<id> in the tmux shim); parent is null for a root pane.
  • list names the atrium that answered: "atrium":"<version>". Key feature expectations on that, never on the presence of a key.
  • Status words are the agsess vocabulary (working, waiting-approval, waiting-prompt, idle, errored, ended) or null for an unbound pane; idle_ms is milliseconds since the pane's last activity.
  • The sidecar stays. ATRIUM_BUS and ATRIUM_BOARD keep their snapshot format; a host that cannot reach the channel (ctl off, or a sandbox between) falls back to them.
  • ping is the liveness probe (0.47.0). The reply is {"ok":true,"atrium":"<version>","uptime_ms":N}, and it is the run loop that writes it, so an answer means the loop is turning. atrium ctl ping [--timeout <ms>] exits 0 on that answer and prints it; otherwise it exits 1 with one line on stderr that starts no endpoint (ATRIUM_CTL unset, or nothing bound there), connection refused (a unix socket left by an atrium that is gone) or timeout (the endpoint took the connection and the loop did not answer). It asks once (on Windows every other verb retries a missing pipe name for up to 30 s), and the timeout bounds the whole exchange, connect included: 1000 ms by default, 30000 at most. A request that fails any other way, or an answer that is not a ping reply (an atrium older than 0.47.0 refuses the verb), is also exit 1.
  • metrics is counts, and only counts (0.47.0). The reply is {"ok":true,"atrium":"<version>","uptime_ms":N,"panes":{"working":N,"waiting-approval":N,"waiting-prompt":N,"idle":N,"errored":N,"ended":N,"unbound":N},"wakes_delivered":N,"held_inboxes":N,"bus_depth":N,"bus_last_seq":N,"open_decisions":N}: every state key is always there (unbound is a pane with no status, the null of list), wakes_delivered counts bus wake lines handed to a pane since the session started (typed into it, or taken by its mod; events that land together for one pane are one line), held_inboxes the inbox --wait connections open now, bus_depth the events in the ring (512 at most), bus_last_seq the newest event's seq (0 before the first) and open_decisions the unresolved decision_needed events. atrium ctl metrics prints them in the Prometheus text exposition format, and --json prints the reply itself:

``text # HELP atrium_build_info The atrium that answered, as the version label; the value is always 1. # TYPE atrium_build_info gauge atrium_build_info{version="0.47.0"} 1 # HELP atrium_uptime_seconds Seconds since the session's run loop started. # TYPE atrium_uptime_seconds gauge atrium_uptime_seconds 90.500 # HELP atrium_panes Panes by state; unbound is a pane with no agent status. # TYPE atrium_panes gauge atrium_panes{state="working"} 2 atrium_panes{state="unbound"} 1 ``

and in the same way atrium_wakes_delivered_total (a counter), atrium_held_inboxes, atrium_bus_depth, atrium_bus_last_seq and atrium_open_decisions (gauges), with one atrium_panes line per state. The only labels are version and state, and state takes the seven fixed names: no role, title or other text a pane chose is ever a label or a value.

  • Probes are not audited. ping and metrics are answered without an entry in the audit log: asked every few seconds for the life of a session, they would push every real action out of its ring. Every other read is still recorded.

The exact reply shapes are pinned by tests in src/ctl/tests.rs (golden_*); a change that breaks one is a wire change and goes in the changelog as such.

Operator tokens: a caller that is not a pane

Every verb that changes state authenticates as the pane whose ATRIUM_TOKEN matches, and is scoped to what that pane spawned. A control endpoint, a bridge, or a person at another shell is not a pane: it has no token of its own, and borrowing a pane's mislabels the audit log and stops at that pane's subtree. An operator token is the credential for such a caller. It is a named token read from a file; it may use the verbs its entry names, on any pane of the session; and every request made with it, allowed or refused, is audited as operator:<name>.

Without a token file nothing changes: no request can authenticate as an operator, and a write with no pane token is refused as before.

The token file

Give the hosting atrium the file's path, as its first argument or in the environment:

atrium --operator-token-file /run/secrets/atrium-operators --allow-ctl claude
ATRIUM_OPERATOR_TOKEN_FILE=/run/secrets/atrium-operators atrium fleet up crew --allow-ctl

fleet up and recover take the flag anywhere among their own flags. On a plain launch it goes first, because past atrium's own flags the arguments belong to the hosted command. A flag in any other place is an error, never a flag quietly dropped: after another session flag or after the command (atrium --allow-ctl claude --operator-token-file F), atrium stops and says where it goes; before the word ctl, it says the client's flag goes after it. A token file needs the control plane: with --allow-ctl off (and not switched on by the fleet or the recovered session), atrium refuses to start rather than run a session no operator can reach. The flag wins over the variable. The variable holds the path; a token is never read from the environment or from an argument.

The file is JSON:

{"operators": [
  {"name": "bridge",  "token": "5f0c…64 hex characters…", "verbs": ["send", "bus pub", "bus resolve"]},
  {"name": "oncall",  "token": "…", "verbs": ["kill", "respawn", "audit"]}
]}

It is read once, at startup, before any pane exists; changing it means restarting atrium. atrium refuses to start, with the reason on stderr, when:

  • on unix, the file is owned by a user other than the one atrium runs as, or has any permission bit set for its group or for others (chmod 600 it). The check is made on the opened file. On Windows the file's ACL is not checked;
  • it is not a regular file, is over 64 KiB, or is not UTF-8;
  • it is not exactly the shape above: an unknown or repeated key, a missing one, or an empty operators list;
  • a name is not 1 to 24 of A-Z a-z 0-9 _ - (shorter than any token, so a file with the two swapped is refused), or appears twice;
  • a token is shorter than 32 characters or longer than 512, holds anything but A-Z a-z 0-9 . _ ~ + / = - (hex and base64 both fit), repeats fewer than 8 distinct characters, or is shared by two entries. Generate one with openssl rand -hex 32;
  • a verb is unknown, named twice, or one of a pane's own (below).

No error prints a token, and none prints a name from the file either: an entry is named by its position (operator #2). With ctl on, the audit log's first rows record each operator's name and verbs (operator-file).

What an entry may name

send, askReach any agent pane in the session: one whose command is an agent CLI (claude, a claude alias, codex, …). A pane running a shell or any other program is refused (see below). A send arrives behind [atrium: from operator:<name>] . A delivery that is dropped leaves a delivery-dropped audit row under the operator's name.

Nothing is granted by default and there is no wildcard: a write the entry does not name is refused. audit is a read with two views: named, it is the whole log; not named, it is the empty list a caller with no credential gets.

Six verbs are about the calling pane and are refused for every operator, and naming one in the file is a startup error: hello, report and whoami (an operator is not a pane and has no mod), inbox (nothing is queued for an operator), bus sub and bus unsub (a subscription wakes the subscribing pane; an operator reads the bus with bus feed).

Where an operator's text may land

send types its text into the target pane and submits it; a bus wake types one framed line. To an agent that is a prompt, and what the agent does with it is bounded by its trust mode. To a shell it is a command line, run with no gate: send 0 "curl … | sh" would be command execution whatever the session's trust. So for an operator, at any trust, skip included:

  • send and ask are refused unless the target is an agent's pane. The test is the command the pane was spawned with (its first word is claude, a claude alias, codex or another agent atrium binds), not what the process is doing at the moment. A mod's inbox does not open another pane to an operator.
  • a send is delivered behind atrium's header, [atrium: from operator:<name>] , like every send (what a pane's request is held to). The agent CLI reads atrium's [ first, so the text may start with anything, ! and / included, and is read as text. (Until the header, an operator's text was refused for those two characters.) It is plain text: newlines and tabs, and no other control character, not even a carriage return.
  • a slash command is run with command, when the entry names that verb and the session's commands list holds the name. The list is the human's; an operator cannot add to it.
  • no argument of an operator's spawn command may open with !, /, # or @: a positional one is the new agent's first prompt, and no header can precede it.
  • a bus pub wake is typed into agent panes only, and into a pane the event merely addresses only when the entry also names send: choosing which pane has text typed into it is what send grants. The event is on the bus either way.

A pane's own send and wake follow the same rules with two exceptions an operator does not get: a pane that is not an agent's takes a pane's text when its mod has an inbox, or when the session is at skip.

How an operator's spawn is bounded

An operator can never exceed the session's launch trust. Its spawn is run as a top-level caller with no privilege:

  • --mode is capped at the session policy like every caller's, and the reply's note says when it was;
  • the command is a bare name found on PATH (claude, codex): anything with a /, a \, a : or a . in it is refused. The allowlist looks at a command's file stem and a path is run as given, so \\host\share\claude.exe would pass as claude and run a binary that honours no posture flag. Every caller's spawn is held to this, a pane's too;
  • the agent allowlist (ATRIUM_CTL_ALLOW aside, agents only), the argv vetting (no raw permission flags, no --mcp-config, --settings or plugin flags), the depth cap and the pane cap all apply;
  • it may run the worker under the session's own identity or none. A root pane may delegate any identity in the vault; an operator may not;
  • --here is refused: there is no pane to tile beside;
  • the worker has no parent and depth 1. It is an ordinary worker, scoped to what it spawns, and is not a root pane.

respawn keeps the target pane's own mode, capped the same way.

What is checked on every operator request

  1. The token is compared in constant time against the operators only. A pane's ATRIUM_TOKEN sent as an operator token matches nothing, and an operator token sent as a pane token matches no pane: the two travel in different fields (operator_token, token) and are never accepted in each other's place. A request with both is refused.
  2. A token that matches nobody is refused, for a read too, and audited as operator:?. The reply is the same whether the session has a token file or not.
  3. Every field is vetted before it is used: bounded in length, free of control characters and of the Unicode characters that reorder or hide text. A role and a worktree name are plain words (A-Z a-z 0-9 . _ -), because they reach a system prompt, a git ref and a path. send and ask text may span lines and nothing else: an escape, a Ctrl+C or a paste terminator is refused. A request refused here is audited with its fields withheld.
  4. The verb is checked against the entry.

Each step that refuses is audited under the operator's name with the reason. A request that does not parse is recorded too, under the operator whose token it carries (operator:? when the token matches nobody); for every caller, the log keeps the parse error's own words and none of the request's values. An operator's requests are all recorded, empty polls included, with one exception: ping and metrics are answered and not recorded, for an operator as for everyone, because a probe every few seconds would empty the log of everything else (a wrong token on one is still recorded). Otherwise so an operator that polls answer or status fills the 1024-entry ring quickly; mirror the log to a file with ATRIUM_CTL_AUDIT where the history matters. An audit entry for an operator has "caller": null and "by": "operator:<name>"; entries for panes are unchanged and carry no by. A worker's own ctl audit never shows an operator's entries.

ctl spawn refuses, for every caller, a role that would read as an operator's label: operator itself (the label of a write with no pane behind it), anything starting operator:, and their look-alikes. Whitespace and characters that do not show are ignored for the comparison; a letter that is not ASCII counts as a possible stand-in for the Latin one; operator followed by any mark other than _ or - is refused; and a role with a : in it must otherwise be plain ASCII (A-Z a-z 0-9 . _ -). operators, operator_2 and team:alpha are ordinary roles. So nothing on the board or the bus signed operator:<name> came from a pane ctl spawn created. A fleet file's role names are a person's and are not checked.

From the client

export ATRIUM_CTL=<the session's endpoint>
atrium ctl --operator-token-file ~/.config/atrium/bridge.token kill dev_3
atrium ctl --operator-token-file operators.json --operator oncall audit 50

The flags go after ctl and before the verb; atrium --operator-token-file F ctl … is an error that says so. The file is either the hosting atrium's own (pick the entry with --operator <name>; it may be omitted when the file names one) or a single token on one line, which is what to hand a client that should know one token and not the others. The same ownership and permission rule applies. The client sends the token as operator_token and sends no pane id and no pane token, even when it runs inside a pane. wait and ask work the same way.

On the wire it is one more field of the one-line request: {"operator_token":"…","cmd":"kill","target":"dev_3"}.

What protects the token, and what does not

  • It never enters a pane's environment. atrium removes ATRIUM_OPERATOR_TOKEN_FILE from its own environment before the first pane is spawned, and the token itself is never in an environment or on a command line.
  • It is in no log, reply, bar message or debug output. The audit log records names; an unparseable request is logged by its length and the parse error's own words; the types that hold a token (the loaded file, a parsed request) print <redacted>.
  • File permissions do not stop a pane. Panes run as the same user as atrium. A 0600 file keeps other users out; it does not keep out an agent in a pane, which can read any file its user can, and on Linux can read the path from /proc/<atrium pid>/cmdline or /proc/<atrium pid>/environ even though its own environment does not have it. Removing the variable is hygiene, not a boundary.
  • What does stop a pane is the deployment: mount the file where the panes' processes cannot read it (a path outside what the agent's sandbox exposes), run the panes under a sandbox or a different user, or keep the token file on the client's side of a boundary and give the host a file only it can read. If a pane can read the file, treat every pane as holding every operator's verbs.
  • The token is the whole credential. Anything that can reach the control channel and present it is that operator, a pane included. The channel itself admits only the same user (a 0600 socket with a peer-credential check; a pipe whose ACL names the logon session), so an operator at another machine reaches it through something you put in front of it. Give each caller its own entry with the fewest verbs, so the audit log names who did what and a leaked token is one line to remove.
  • An operator with send can make any agent do what that agent's trust mode allows, and no more. send types a prompt into an agent's pane as the human would, and the agent acts on it under the mode it was started with. In a skip session that is anything; in a plan session it is reading. The launch trust is the ceiling, which is why an operator can never raise it, and why the text is refused for a pane that is not an agent's: a shell has no mode. What this does not cover: whatever an agent CLI's input line treats specially in the middle of a prompt (atrium's header is the first thing in it; what the CLI makes of the rest is the CLI's), and a pane whose command is an agent's name but resolves to something else on PATH. The first is the agent's input handling; the second is whoever controls PATH and the working directory of the hosting atrium.
  • kill and respawn reach the human's own panes. An operator that holds them can end the session.

The mod: typed tools, the role section and subagent panes

With atrium mod install done, every claude pane carries a plugin (the mod, mod/) that speaks the verbs above for it and gives the model three things:

  • Typed tools. atrium_spawn, atrium_send, atrium_status, atrium_list, atrium_kill, atrium_board_set|get|list|claim|release and atrium_bus_pub|feed|resolve|topics: each call is one atrium ctl run with the pane's own token, and the reply is what the model reads. The shell verbs stay the same surface, so the skills and the docs remain true either way. A permission ask for one of these tools is answered by the mod, never a dialog; a deny from a rule stands.
  • The role section. An atrium:role section of the system prompt, from whoami: the pane, its role, parent, depth and trust mode, its item on the board and the files that item owns, its worktree, whether it may spawn, and what a [atrium bus # line is. Re-read every turn, so a lead's re-brief lands. When the item owns files, an Edit, Write or NotebookEdit anywhere else is refused by real path with the owner named.
  • Native delivery. A pane whose mod declared inbox is never typed into: its sends and wakes wait in the queue until the mod collects them with inbox and submits each through the engine's prompt queue, which starts a turn only when the session is idle. The draft and dialog races the pty path guards against (src/deliver.rs) do not arise, and a task may span lines. A pane without the cap keeps the pty path.
  • The /atrium pane. Inside Claude Code, /atrium opens a pane with the open decisions (each with a resolve button and a hotkey), the board, and the last bus events the pane subscribes to, refreshed every 3 s while open; a band above the prompt counts the open decisions and opens the pane. With a fleet's respawn_at, a pane whose context fill crosses the threshold while idle gets one decision_needed posted to its parent on the atrium topic, with the parent woken: the lead's "respawn when heavy" rule becomes a number it is asked about.
  • Sight: captions, the collision radar and asks. The mod reports a caption on every tool call, free of charge (running cargo test, editing filter.rs, reading main.rs) and, when the fleet says captions: true, a six-word caption from the model's own words every twenty seconds or so of streaming (one small haiku call); the overview shows it in place of the transcript's last action and the tile draws it dim after the title. It reports the real path of every Edit, Write and NotebookEdit that ran, and the broker keys each by the pane's worktree, so two worktrees' copies of src/x.rs are one file: the first time two live panes edit it, both tiles and overview rows wear ⚡, the overview lists the file under the agents, and one collision decision_needed goes to the nearest pane above both (the lead) on the atrium topic, or to the human when there is none. atrium ctl who <path> answers who has a file, before the merge. And atrium ctl ask <target> <question> (or Ctrl+A ? on a tile, or atrium_ask from a pane) puts a question to a pane's mod, which answers from a fork of the pane's own context: the turn is untouched, nothing is appended to its context, and the transcript never leaves the pane; the reply opens as an overlay for the human and returns as the tool's result for an agent.
  • Subagents as panes. Under the session's subagents policy (panes, the default; a fleet may say native or deny), the model's Agent tool is refused with a pointer to atrium_subagent, which spawns a claude pane beside the caller (--here), sends it the task, waits for the answer the child's own mod reports, closes the pane unless keep or the fleet's subagents_keep, and returns the answer. Every subagent is a tile the human can watch, send to and kill.

What the broker believes of a mod is bounded: a report is about the reporter (a target is refused), an answer is capped, scrubbed and read only up the spawn tree, and a mod cannot widen trust (it rewrites an ask to allow for its own tools only; a deny is never overridden). See trust and security.

Delegation skills: atrium-delegate, atrium-coordinate and atrium-fleet

ctl is the mechanism; three Claude Code skills (in skills/) are the instruction layer that makes an agent use it. Copy the directories into ~/.claude/skills/ and any atrium-hosted claude picks them up. The first two exist because the trigger is who decides to delegate:

  • atrium-delegate (ambient / discretionary): the agent may hand off an independent, substantial part when it genuinely pays, and does small or dependent work inline. On its own a capable agent usually judges it can do the work itself (which is correct), so this fires rarely by design. Its real value is discoverability: without it, an agent does not know atrium ctl exists at all.
  • atrium-coordinate (directed): for when you want fan-out. It casts the agent as a coordinator that splits the work, delegates every part, monitors, collects, and reaps, instead of implementing inline. This is the reliable lever: on a task where the ambient skill chose inline every time, coordinate mode fanned out every time.

The third covers the saved-fleet path rather than ad-hoc delegation:

Claude Code's own teams, as atrium panes

Claude Code has a teams feature of its own: a lead spawns teammates, hands them tasks from a shared list, and messages them through mailboxes. In split-pane mode each teammate gets a pane, but Claude Code does not draw panes. It runs a program named tmux, asks it for a split, reads the new pane's id back, and later kill-panes it. Its backend knows two pane managers, tmux and iTerm2, and picks tmux whenever TMUX is set in the lead's environment. On Windows there is neither, so teams fell back to in-process rows inside the lead.

How the teammate gets into the split has changed between releases, and atrium serves both ways. They were read from the code inside two installed Claude Code binaries, 2.1.289 and 2.1.325; atrium's tests carry the 2.1.325 command lines as fixtures and drive the sequence through the real shim with a stand-in for the lead, and a live 2.1.325 lead has started a teammate this way once, on Windows (what was seen and what was not). A release that changes the sequence again is refused where it differs, with a message that says so, until atrium is taught it.

Claude CodeThe lead's callsUnder atrium
2.1.289split-window -d -t @0 -h -l 70% -P -F '#{pane_id}' -- claude --agent-id … --agent-name …: the teammate's argv is on the split.ctl spawn --here: the argv is a spawn's command, held to a spawn's rules.
2.1.325split-window -d -t %0 -h -l 70% -P -F '#{pane_id}' -- cat (a placeholder), the style and title calls, set-option -p -t %1 remain-on-exit failed, then respawn-pane -k -t %1 -- '<one shell command line>'.A placeholder pane, then atrium starts the teammate in it: see the placeholder and the teammate.

With the control plane on, atrium answers to the name. A claude pane in an --allow-ctl session is born with:

  • TMUX=<ctl address>,<atrium pid>,0 and TMUX_PANE=%<pane>: what Claude Code's auto-detection looks for;
  • a PATH led by <state root>/shim/, holding tmux (tmux.exe on Windows, since the native Claude Code resolves executables only). It is atrium's own binary under a second name, placed on the first claude spawn and refreshed when atrium is reinstalled;
  • CLAUDE_CODE_TMUX_TRUECOLOR=1, so Claude Code keeps truecolor instead of assuming a real tmux in between.

Invoked as tmux, atrium serves the verbs the teams backend uses, each one an atrium ctl request with the caller's own token: -V, display-message -p, list-panes -F, list-windows -F, split-window, new-window, respawn-pane, kill-pane and send-keys. Layout and style verbs (set-option, select-pane, select-layout, resize-pane, show-environment, has-session, new-session, switch-client, attach-session) are honoured by doing nothing, set-option … remain-on-exit among them. -S <socket> and -L <name> in front of a verb (2.1.325 leads every call with -S) are skipped. capture-pane is refused: atrium never hands one pane the text of another. Anything else exits 1 with a message.

So a teammate is an ordinary atrium pane: split-window is ctl spawn --here (--no-focus for tmux's -d, which Claude Code passes, so your keyboard stays where it is), the pane's role is the teammate's --agent-name, it is a child of the lead in the spawn tree and under its trust ceiling, and it has the status border, the overview row, the board and the bus. The shim models one window, @0, whose panes are the caller and its direct children, which is the team as the lead sees it; pane ids are %<agent id>.

Where a teammate lands follows the split's target. Claude Code's first teammate splits the window or the lead's own pane (-t @0 in 2.1.289, -t %<lead> in 2.1.325), so it goes beside the lead; each later one splits an existing teammate's pane (-t %N -v or -h), and the shim passes --beside <N> so the new pane goes next to that teammate. A target that is not in the lead's window falls back to the lead, and the spawn reply's note says so. The split's size is honoured: the shim passes -l as --size, so the first teammate's -l 70% gives it 70 % of the lead's width and the lead keeps 30 %. The ratio lives on the split, so a terminal resize keeps the share, and a later teammate (-t %1 -v, no -l) re-grids only the half it lands in: the teammates tile inside their 70 % and the lead's 30 % does not move, as under tmux. A -l in cells (-l 20) is that many columns of the target pane. -h and -v are accepted too; the window's own orientation decides.

The team's task list shows in the overview (Ctrl+A o). Claude Code keeps a team under ~/.claude/teams/<team>/ (config.json: the lead and the members; inboxes/: their mailboxes) and its tasks under ~/.claude/tasks/<team>/, one JSON file per task with its subject, status (pending, in_progress, completed), owner and blockedBy. The team is named session- plus the first eight characters of the lead's session id, which atrium minted at spawn, so atrium knows where to look without being told ($CLAUDE_CONFIG_DIR is honoured). Under the lead's row the overview lists the team, one line per task: [ ] pending, [~] in progress, [x] completed, each with its owner and the tasks still blocking it; a teammate's row carries its current task as the caption when its mod reported none. The files are read only while the overview is open, at most once a second, and only a file whose stamp changed is read again. The team leaves the overview when the lead's session ends and Claude Code removes the team directory (the tasks directory stays behind, and is not a live team). The files are Claude Code's: atrium never writes them.

Three things to know:

  • It is a setting. "teams": "off" in config.json turns it off for every session on the machine; teams: "off" in a fleet turns it off for that fleet, and a fleet's own key wins over the config's. "show" is the default. Off means the pane gets no TMUX and nothing on its PATH, so Claude Code's teams run in-process as they did before. The fleet preflight names which is in effect.
  • Claude Code's teammateMode setting defaults to in-process. Set it to auto (split panes when inside tmux, which an atrium claude pane now is) or tmux.
  • atrium --tmux-shim <tmux args…> reaches the shim by its real name, for a probe: atrium --tmux-shim -V prints tmux 3.5a-atrium.

Which path handles a named teammate. In Claude Code 2.1.325 there is no separate team-creation tool: a lead starts a teammate by calling its Agent tool with a name, and teams need CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 in the lead's environment. What happens to that call in an atrium claude pane depends on two settings. With atrium's mod installed and on, the mod takes over the Agent tool and opens the pane itself through atrium ctl; the call never reaches the shim. With the mod off and teams not off, Claude Code's own teams backend runs and finds the shim: the sequence above. With the mod off and teams: "off", or with the control plane off, neither applies, and the teammate runs in-process inside the lead as it does without atrium.

The shim speaks only for the pane that runs it, with that pane's token, so it can spawn and kill only inside that pane's subtree, like any atrium ctl caller, and its requests are held to the same rules: the command of a split-window is a bare name on the agent allowlist with the flags a teammate may choose, and send-keys is a send. atrium cannot tell the shim from any other holder of the pane's token, so there is no wider rule for it. The two requests below exist for the shim, and are written so that any holder of a claude pane's token gets from them exactly what the shim does.

The placeholder and the teammate (Claude Code 2.1.325)

The placeholder. split-window … -- cat does not run cat, and cat is still not a command a pane may spawn. A split whose whole command is that one word becomes ctl spawn --here --hold: a request that names no command at all (it may not carry one, nor a role, an identity, a mode or a worktree). atrium starts its own binary in a mode that prints waiting for a teammate and waits to be killed (atrium --tmux-hold, started from atrium's own executable path). The pane is placed like any --here split (the -t target as --beside, -l as --size, -d as --no-focus), is a child of the caller, counts in list-panes and in the pane cap, and takes the title and colour calls (which do nothing). It is marked as a placeholder made by its caller, and:

  • it is granted only to a claude agent's pane that may create teammates, under the depth cap and the pane cap of any spawn, in a session where teams is not off. A shell, another agent CLI, an operator and a placeholder get none;
  • it has no token and no ctl environment, so it can make no request and none authenticates as it; nothing typed into it goes anywhere;
  • it takes no text at any trust: a send to it is refused and a wake skips it, at skip too. It is neither an agent's pane nor a shell, and whatever were queued for its pane id would be typed into the teammate that takes the id over (anything found queued for it when the teammate starts is dropped);
  • a plain ctl respawn of it is refused; its lead (or anything above its lead) may kill it, and so may you. One that is never used just sits there until then;
  • it belongs to the process that asked for it. If its lead pane is respawned, the placeholder stays that pane's child and can be killed by it, but nothing can start a teammate in it any more; the same if its lead exits. atrium recover brings a placeholder back as a pane running the waiting program, not as a placeholder: it cannot be claimed either.

The teammate. respawn-pane -k -t %N -- <line> becomes ctl respawn N --teammate <line>. It is served only when pane N is a live placeholder that the calling pane itself made, the caller is a claude agent's pane that may create teammates, and teams is not off. Every other target is refused with one message: an agent's pane, a shell, the caller itself, another lead's placeholder, a child's own placeholder, and the same pane a second time (the mark is cleared when the teammate starts). So no request re-points a pane that already runs a command.

The line is a POSIX shell command, written for tmux to run with sh -c:

[sh -c '{ echo $PPID > "$1"/cgroup.procs; } 2>/dev/null' sh <dir>; ]
cd <cwd> && env <NAME=value>… <program> --agent-id … --agent-name … --team-name … [more flags]

atrium never hands it to a shell, on any platform (on Windows there is no sh, cd or env to hand it to). It is parsed against exactly that grammar: the optional first line is Claude Code's Linux tool-cgroup prefix, recognised and dropped (atrium places the process itself). Words follow POSIX quoting. Outside quotes only A-Z a-z 0-9 _ . / : = @ + , - is a word character, so ;, |, &, $, a backquote, (, ), <, >, *, ?, ~, #, a second &&, any control character and a newline are each a refusal that says what was found. A line over 24 KiB is refused too, by the shim before it is sent: the usual cause is a lead started with a very large inline --mcp-config, which Claude Code repeats on the line (atrium would drop that flag anyway; put the config in a file). respawn-pane given tmux's own -c <dir> or -e VAR=val is refused rather than served with the option ignored. Any other directory is refused, a subdirectory of the project included: a claude started in a directory of the request's choosing would load that directory's .claude/settings, .mcp.json and CLAUDE.md, with its folder trust pre-accepted by atrium, which a plain ctl spawn never lets a pane choose.

The pane then stops being a placeholder and is a ctl-spawned claude pane in every other respect: it has a token, ATRIUM_CTL / ATRIUM_PANE, the shim's TMUX (so a teammate may lead a team of its own, one level deeper, under the depth cap), --session-id, atrium's --settings, the deny list and the build pool. Two audit rows are written under the lead: respawn with the names of the flags the line carried and how many environment assignments (teammate flags=--agent-id,… unknown=0 env=57), and teammate with what atrium decided (pane=4 role=researcher mode=accept env_dropped=54 flags_dropped=--settings), whose note is the line about variables that were not passed on, when there is one. They carry one value from the line, the role, which is --agent-name after its shape check (a letter or digit, then letters, digits, _ . - and single spaces). Nothing else of the line is in them: not the verify key, not a path, not a model, not a variable's value. A line that does not parse is recorded by its length.

A teammate's environment

Under a real tmux a teammate gets whatever the lead's command line assigns. Under atrium it gets, in this order:

  1. What atrium gave its lead. The teammate starts from atrium's own environment, like every pane, and then gets what atrium itself added for the lead pane, taken from atrium's record of that pane and never from the request: the lead's identity (the credentials atrium resolved for it from its name; the name is what atrium keeps, and they are resolved again for the teammate), its fleet context variables, and its program (the first word of its command, argv[0], not its other arguments), so a lead started as a claude_aliases wrapper with its own config directory has teammates started through the same wrapper, on the same account. A lead with no identity gives none. The request cannot name an identity: a teammate respawn that carries one is refused, so this cannot be used to reach an identity the lead does not hold. The per-pane values (ATRIUM_PANE, ATRIUM_TOKEN, TMUX_PANE) are the teammate's own.
  2. The three team variables: CLAUDECODE=1 and CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1, always, and CLAUDE_CODE_TASK_LIST_ID=<id> when the line has it (held to a name's shape).
  3. Your teams_env list. An array of environment variable names in config.json or in a fleet ("teams_env": ["AWS_PROFILE", "HTTPS_PROXY"]), empty by default. A fleet's list replaces the config's, an empty one included; a session brought back with atrium recover uses the config's. For a listed name, the line's assignment is set on the teammate, if its value is plain text (no control or hidden character, at most 4096 bytes; otherwise the launch is refused). A name is a letter or _ then up to 63 of A-Z a-z 0-9 _; on Windows it matches in any case, as the environment itself does. Nothing a ctl request says adds to the list.
  4. Never listable, in any case, and a file that lists one does not load: any name containing SKIP_PERMISSIONS; any ATRIUM_ name; TMUX, TMUX_PANE; PATH, PATHEXT; NODE_OPTIONS, BUN_OPTIONS, CLAUDE_CODE_PLUGIN_DIRS, LD_PRELOAD, LD_LIBRARY_PATH, any DYLD_ name; BASH_ENV, ENV; ComSpec, SHELL, CLAUDE_CODE_SHELL; GIT_SSH_COMMAND, any GIT_CONFIG_ name; CARGO_MAKEFLAGS; and CLAUDE_CODE_TEAMMATE_COMMAND. Each would load code into the teammate, choose the shell or the programs it runs, or stand in for something atrium sets.
  5. Listable, with a warning: CLAUDE_CONFIG_DIR, HOME, USERPROFILE, APPDATA, ANTHROPIC_BASE_URL, any name ending _PROXY, NODE_EXTRA_CA_CERTS, SSL_CERT_FILE and SystemRoot move where a teammate reads its settings and credentials from, or where its traffic goes. They are what the list is for (a proxy is the common case), so they are allowed, and named after WARNING: wherever the list is shown.
  6. Shown before the session starts, when it is not empty: in the fleet's launch banner; on a plain --allow-ctl launch, as one line on stderr before the terminal is taken; and by atrium config path, which also says why a file does not load.
  7. Everything else is dropped, and named. Claude Code forwards the lead's provider, proxy and config variables on the line (ANTHROPIC_*, AWS_*, CLAUDE_CONFIG_DIR, HTTPS_PROXY, …) and a skip-permissions variable. Each one that is neither applied nor listed is compared with the value the teammate has anyway from atrium's own environment and the non-secret variables above (an empty value counts as an unset variable). Most are the same, because the lead got them from atrium too, and nothing is said of those. The ones that differ are named in one line, on the bar, in the reply and in the audit log: teammate researcher: 2 variable(s) from the lead were not passed on: ANTHROPIC_BASE_URL, HTTPS_PROXY; add them to teams_env to pass them. Names only, at most eight and then a count; never a value. A variable the lead's identity sets is left out of this altogether, neither compared nor named: the teammate has atrium's value for it by design, and saying whether a value on the line matched it would let a request test guesses of a credential. On Windows the case variants of one name are one variable, compared once.

The list is opt-in because of where the line comes from. atrium cannot tell Claude Code from any other process that holds the lead pane's token, and a base URL or a proxy accepted from such a request would route a teammate's prompts, and the credentials it sends with them, wherever the request said. Listing a name is your statement that, in this session, a pane may choose that variable for its teammates.

What a teammate does not get, and what is still open

What a teammate does not get that it would under a real tmux: a forwarded variable that differs from what atrium gave the lead and is not on teams_env (it is named, as above); a CLAUDE_CODE_TEAMMATE_COMMAND or launcher wrapper; the lead's --settings, --mcp-config, --plugin-dir and --setting-sources; its --agent-type; a deny rule for an MCP tool by its bare name (the launch is refused instead); a working directory other than its lead's; and a permission mode above its lead pane's. A later ctl respawn of a teammate restarts it as any pane: under a new pane id, which Claude Code does not learn, without the three team variables, and without a --permission-mode atrium wrote for a plan, default or dontAsk request (its governed mode is kept).

What has been seen running. One live run: a real Claude Code 2.1.325 lead on Windows, the mod off, CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1, a headless fleet at automode, starting one named teammate with its Agent tool. atrium's audit log showed the placeholder (spawn hold beside=0 size=70%), the request (respawn target=1 teammate flags=--agent-id,--agent-name,--team-name,--agent-color,--parent-session-id,--lead-verify-key,--permission-mode,--disallowed-tools,--settings,--model) and the decision (teammate pane=1 role=scout mode=automode env_dropped=8 flags_dropped=--settings). The teammate started, bound to its session and ran, and Claude Code's team file recorded it with the tmux backend as pane %1. The line's directory was the lead's own.

What has not. The teammate's message arriving back at its lead; anything on Linux or macOS (the cgroup prefix among it); a second teammate in the same team; --agent-type. Two questions are open, each with the live test that would settle it:

  • Does an agent definition outrank the mode atrium passes? In a session at accept, write .claude/agents/probe.md with permissionMode: bypassPermissions and a hook in its frontmatter, have atrium pass --agent-type probe to a teammate, and see whether the teammate edits and runs commands without asking and whether the hook runs. Until that is known, --agent-type is dropped.
  • Can a pane approve its own teammate's permission prompts? --lead-verify-key, --parent-session-id, --agent-id and --team-name all come from the line, so whoever holds the lead pane's token chose them. If Claude Code answers a teammate's permission prompts through the team mailbox and checks the answer against this key, a script holding that token could write the approvals itself. The test: start a teammate at plan or default through the shim with a key pair of your own, write an approval into its inbox signed with that key, and see whether a prompt is answered. atrium's ceiling on a teammate is the permission mode it passes. Claude Code's own in-team approval flow happens between its processes and its files, outside anything atrium can bind.
